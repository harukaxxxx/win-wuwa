# Issue 12 — local bounded slice

No real Discord credentials, Discord account, remote D1, deployment or device were used.

## Official documentation examined

- [Get Current User Guild Member](https://docs.discord.com/developers/resources/user#get-current-user-guild-member): `GET /users/@me/guilds/{guild.id}/member` requires `guilds.members.read`.
- [OAuth2 scopes](https://docs.discord.com/developers/topics/oauth2#shared-resources-oauth2-scopes): the scope authorizes this current-user member endpoint.
- [Guild member object](https://docs.discord.com/developers/resources/guild#guild-member-object): `pending` is optional.

## Implemented locally

Contextual OAuth requests `identify` plus `guilds.members.read` for a restricted activity and `identify` otherwise. The callback checks membership only for restricted activities and stores a five-minute result tied to session, user, owner, activity, rules and guild; it does not persist the access token. The registration INSERT conditionally checks the live session, owner approval, activity state and matching member proof in one SQL statement. Existing registrations remain idempotent after proof expiry. The authenticated viewer self endpoint exposes only that session's status and optional retry delay; the viewer interface includes a reauthorization link and status copy. The migration preserves old OAuth context rows; old rows have no guild snapshot and cannot produce a member proof.

At the earlier HTTP-test stage, synthetic HTTP/real D1 tests covered scopes, the unrestricted no-membership-call path, member, nonmember, pending, reauthorization, rate limit, server failure and malformed body, session isolation and idempotent retry. These tests do not prove real Discord status semantics or behavior of scope changes on existing provider grants; subsequent browser checks are reported below.

## Follow-up implementation and limits

The prior isolated baseline was 63 passing and one failing: the invitation product assertion returned 400 instead of 200. The follow-up adds migration 0010, invite validation, saved defaults and immutable activity snapshots including exact retries, and owner/viewer controls. The member callback now requires a matching `user.id`, the documented required member fields and the granted OAuth scopes; only a Discord JSON 404 code 10007 is classified as nonmember. Official [OAuth token example](https://docs.discord.com/developers/topics/oauth2#authorization-code-grant-access-token-response) includes `scope`; the [JSON error codes](https://docs.discord.com/developers/topics/opcodes-and-status-codes#json) distinguish 10007 Unknown Member from 10004 Unknown Guild. The guild member documentation marks `user` optional generally, but does not establish that this particular endpoint omits it. Therefore absence is deliberately rejected rather than assuming membership. This may reject real members if Discord omits that field; real-provider verification is required before release.

Synthetic D1/HTTP tests cover incorrect identity, malformed required member fields, invalid dates and roles, pending, missing granted scope, 404 variants, proof bindings and expiry, and disabled/paused write guards. A prior registered user's retry does not call Discord again. Invite tests use only synthetic URLs, verify locked snapshots in open and paused states and cover the old-schema migration. The final exact test count belongs to the execution report, not this narrative.
